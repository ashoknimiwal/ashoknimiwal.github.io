ExposureIQ

Active research Private repo

Measuring how exposed public companies are to emerging risks, from what executives say on earnings calls.

ExposureIQ ingests a five-year panel of U.S. earnings calls and classifies each text segment against a risk theme through a cooperative multi-agent pipeline, where four specialist agents share findings on a blackboard before voting. The harder half of the project is the evaluation harness: it scores not just the system's output but each agent inside it, records enough provenance to reproduce any number, and diffs runs example-by-example — so a prompt tweak can't quietly trade good answers for bad ones.

106,597 Text segments
1,000 Earnings calls

There's a conversational version of this. ThemeScope is a chat interface built on top of this pipeline — ask in plain English and get answers traced all the way back to the sentence an executive actually said.

The Problem

Emerging risks — integrity failures, compliance exposure, governance breakdowns — show up in executive language long before they show up in filings or headlines. Earnings calls are a dense, quarterly, cross-sector source of that language: a standing invitation to measure something that financial statements cannot see.

Two things make that hard.

The signal is multi-label and boundary-fuzzy A single answer in a Q&A session can touch accountability and honesty at once, or neither. Reasonable annotators disagree on where one component ends and the next begins — so the ground truth is itself contested.
An LLM pipeline you can't decompose can't be trusted End-to-end F1 tells you the system is wrong. It does not tell you whether the gate dropped the segment, an agent hallucinated evidence, or the synthesizer overrode a correct vote.

Plenty of work treats the first as the interesting problem. ExposureIQ treats the second as the actual engineering problem — a pipeline making up to ten model calls per input is only as useful as your ability to say which call is wrong.

How It Works

Every segment is classified against a risk theme. The first theme is corporate integrity, broken into four components — Accountability, Compliance, Moral Integrity, and Honesty. A segment can carry any combination of them, or none. Classification runs through a five-stage cooperative blackboard, at most ten LLM calls per segment:

1
Gate — is this segment relevant at all? A cheap, recall-optimised call filters out irrelevant segments before any specialist agent runs.
↳ not relevant — stop here, nine downstream calls skipped
|
2
Observe — four component agents, in parallel Each agent posts a factual observation about the segment to a shared blackboard. No judgements yet, only what each one noticed.
|
3
Verdict — the same four agents, now reading their peers Each votes yes or no on its own component with reasoning, having read every other agent's notes first.
|
4
Synthesize — consolidate the votes A synthesiser turns four independent votes into the final multi-label output.
|
5
Force — conditional, fires only on an empty result When nothing at all was labelled, the system commits to one best fit and marks the answer as forced.

Three design points

The gate is the cost lever. One cheap call avoids nine expensive ones. It currently avoids 43% of downstream work at 2.7% leakage — the single largest determinant of what the system costs to run, and the reason a 100k-segment corpus is tractable at all.
The blackboard is the cooperative step. Agents observe before they judge, and judge only after reading each other. Honesty can lean on what Accountability noticed. Splitting observation from verdict is what makes the cooperation real rather than four independent classifiers wearing a shared name.
Forcing is a designed signal, not a fallback hack. When the system labels nothing, it is made to commit to one component and mark that answer as forced — turning genuine ambiguity into a measurable rate instead of a silent empty result.

Evaluation: the actual hard part

Most work with LLM pipelines stops at "the output looks good." The harness is built on the opposite premise — and it is the larger half of the project.

It is deliberately theme-agnostic. Metrics never see a pipeline object. An adapter flattens whatever ran into views, each one a single comparable quantity, and a task binds a view to a set of metrics. Everything downstream — metric dispatch, storage, reporting, regression diffing — is driven off the task list.

pipeline run → adapter → views → tasks → metrics

The payoff is that extending the system is cheap and the cost is predictable:

To add… You change
a metric register it, name it in a task
an agent or stage emit one more view, declare one more task
an entire new theme, with a different architecture one adapter class

Six tasks, one per hand-off

Each hand-off in the pipeline is scored separately, so an error can be attributed to the stage that produced it rather than to the system as a whole:

Task What it scores
gate Whether the relevance filter kept what it should have
observations The notes each agent posts to the blackboard
verdict_labels The stage-3 votes, scored as if they were the answer
final_labels The system's actual output
synthesis The hand-off from votes to final labels
system Errors, calls, tokens, latency, cost

What that bought

Scoring the same run at two different stages answers a question end-to-end F1 cannot even express — is the synthesiser helping?

Scoring stage-3 votes as if they were the final answer gives micro F1 0.673. The actual final output scores 0.698. The synthesiser is adding 2.6 points — filtering over-eager votes rather than destroying signal.

Had the inequality run the other way, the fix would belong in stage 4 — and end-to-end F1 alone would never have said so.

This is a diagnostic claim rather than a leaderboard number, and it is the kind of claim the harness exists to make. It points at a specific stage, and it implies a specific fix.

Engineering details

A few pieces that read as real work rather than a tutorial project:

Gold fingerprinting. Every evaluation stores a content hash of the gold labels. Relabel one example and the fingerprint moves, flagging every comparison against an older evaluation as not-like-for-like. It is the difference between "my F1 went up" and "my F1 went up on a different test set", and the CI gate treats a fingerprint mismatch as a hard failure.
Groundedness without ground truth. Any span an agent puts in quotes must actually appear in the source segment. A note quoting text that isn't there is fabricating evidence the next stage then reasons over — so it is caught, even though there is no gold label for it. Whitespace and smart quotes are normalised so a reflowed quote isn't miscounted as a fabrication.
Re-scoring is free. Metrics evolve faster than runs do, so any historical run can be re-scored under a new metric without spending a token. Fresh predictions are opt-in.
Metrics implemented from scratch. Rather than pulled from scikit-learn — the definitions are short, the project stays dependency-light, and every averaging convention is explicit and unit-tested, so a reported F1 has exactly one meaning.
Reproducibility is recorded, not assumed. Every run records its prompt version and content hash, the archived prompt text, per-stage models, a config snapshot, and the git commit. A dirty git tree is recorded as dirty and the report carries a warning — a run against uncommitted code isn't reproducible and shouldn't pretend to be.

Known gaps

Documented rather than buried — the open questions are part of the process, not an embarrassment to hide from it:

No single-agent ablation yet. Whether the five-stage blackboard beats one well-prompted call is still open. The harness makes the comparison cheap; the run hasn't been done.
Component gold labels are model-generated. Only the relevance label is human-annotated. Component-level F1 therefore measures agreement with a reference model, not agreement with truth.
Cooperation is proxied, not proven. The blackboard-influence metric counts cross-component references in reasoning. Only an ablation settles whether cooperation earns its cost.
